# v0.6 mastery audit

This audit deliberately separates implemented evidence from portfolio narrative. The goal of v0.6 is
not to add another topic, but to make the existing layers defensible through one cross-layer system.

## What became meaningfully deeper

| Area | Strong evidence | Why it is stronger than a demo |
| --- | --- | --- |
| Data structures | `hash_table.hpp`, `min_heap.hpp`, `bplus_tree.hpp`, `data_structures.hpp`, differential tests | Custom behavior is checked against reference containers and benchmarked under fixed workloads. |
| Concurrency | lost-update fixture, mutex/atomic comparison, product queue claim tests | The project shows an incorrect fast path and the ownership boundary that fixes it. |
| Storage | page-backed toy table, B+tree lookup, reopen/rebuild tests, fsync boundary | Rows are serialized into pages and reopened rather than only kept in memory. |
| OS boundary | process/fd experiments, xv6 source reading, sample trace, fd identity tests | Claims are tied to observed POSIX behavior and narrowed kernel source paths. |
| Embedded boundary | simulator-first HAL, ring buffer, protocol parser, scheduler jitter, fault injection | The repo does not pretend a board was used; it models firmware constraints explicitly. |
| Cross-layer integration | `durable-job-runtime` capstone | Networking, parser, queue, scheduler, journal, recovery and index are now exercised in one path. |

## What is still demo-level or intentionally narrow

- The HTTP server is a blocking/threaded learning server, not an event-loop runtime.
- The B+tree is in-memory and the storage engine persists row pages, not persisted B+tree pages.
- The filesystem model is an inode/block simulator and does not implement journaling, free-space
  management or crash-safe ordering.
- The firmware track is simulator-first. Physical GPIO, UART baud timing, real ISR latency, binary
  size, RAM usage and stack usage remain unclaimed.
- Assembly/debugging evidence is useful but narrow. LLDB failed in the local environment; `sample`
  produced a trace, but this is not kernel debugging.

## What is documentation-heavy

- PostgreSQL source reading is a bridge only. No real product `EXPLAIN (ANALYZE, BUFFERS)` evidence is
  committed yet.
- CPU cache / branch behavior is only a roadmap item.
- Advanced lock-free algorithms, NUMA, production filesystem internals and kernel driver work are not
  implemented.

## Benchmark reproducibility

The benchmark path is reproducible to the extent that a clean clone can build the C++ labs and run:

```bash
make clean
make -j2 all
make test
make lint
python3 tools/run_labs.py --profile quick
```

Release snapshots store source SHA, compiler, OS, flags, input sizes and normalized CSV rows. Numeric
results are not universal; they are observations for the captured environment.

## Mastery-level corrections

The existing level contract remains useful if read strictly:

```text
0 Not Started
1 Explained
2 Implemented
3 Tested
4 Benchmarked
5 Applied to Real Project
```

v0.6 adds a separate `defense_status` instead of inflating level numbers. A topic can be Level 4 or
5 and still not be fully defended if the explanation path, failure mode, trade-off and source file
locations are not documented.

Topics that must stay conservative after v0.6:

- `physical GPIO / serial / interrupt`: Level 0.
- `PostgreSQL EXPLAIN / BUFFERS`: Level 1.
- `MVCC / isolation / WAL`: Level 0.
- `async I/O / event loop`: Level 1.
- `advanced lock-free algorithms`: not claimed.

The capstone is not proof of a production queue service. It is evidence that the same engineer can
connect the layers and explain the invariants that keep the system from losing or duplicating logical
work under selected deterministic failures.

## v0.7 reality-check follow-up

v0.7 narrows several conservative v0.6 items through real runtime evidence:

- `PostgreSQL EXPLAIN / BUFFERS` moves from docs-only to measured real PostgreSQL evidence.
- `MVCC / isolation / WAL` becomes a bounded reality check: visibility, lock wait, deadlock and WAL
  LSN movement are observed, but full PostgreSQL MVCC/WAL implementation is still not claimed.
- `async I/O / event loop` moves from roadmap to a macOS kqueue lab with a Linux poll fallback.

The physical hardware item remains Level 0 because no Pico, ESP32, Arduino or USB serial board was
detected.
