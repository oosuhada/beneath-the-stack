# v0.7 reality check: real systems validation

v0.7 is not a new-topic sprint. It asks whether the controlled systems models built in earlier
versions still explain behavior when the project touches real runtimes: PostgreSQL, macOS kqueue,
and sanitizer/debugging tooling.

## A. PostgreSQL deep trace

`tools/run_postgres_reality.py` creates a disposable local PostgreSQL database, loads 20,000 rows,
and records `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` output plus concurrency experiments.

Observed on the MacBook Air:

- PostgreSQL 18.4 was available through Homebrew and accepted local connections on `/tmp:5432`.
- a broad `status = 'done'` aggregate used `Seq Scan`;
- a composite `(account_id, status, priority DESC)` query used `Index Scan` under a `Limit`;
- a selective predicate used `Bitmap Index Scan` + `Bitmap Heap Scan`;
- an uncommitted update was invisible to a second transaction until commit;
- a row-level lock wait was observed through `lock_timeout`;
- a two-row cycle produced PostgreSQL deadlock detection and aborted exactly one side;
- `pg_current_wal_lsn()` advanced after an update workload.

This is real PostgreSQL evidence, not a claim that the toy B+ tree implements PostgreSQL. The toy
code remains useful for explaining pages and indexes; the PostgreSQL script validates where that
model becomes incomplete: planner choice, buffer accounting, tuple visibility, lock waits and WAL.

## B. Event-driven networking

`labs/event_loop_reality/main.cpp` compares three socketpair-based workloads:

```text
blocking serial read
thread per client
event loop
```

On macOS the event-loop path uses `kqueue`; on Linux CI it compiles through a `poll` fallback. The
workload deliberately splits writes into chunks and delays one peer so the experiment measures
partial reads and slow/idle peer cost, not internet throughput.

The first event-loop implementation was wrong: kqueue can report EOF after the final bytes are
drained, and the loop originally failed to close a connection when EOF arrived with no more readable
bytes. That caused occasional hangs or incomplete byte counts. The fixed version treats EOF as a
close condition after draining pending bytes.

## C. Real hardware

Hardware is still not claimed. The MacBook Air probe saw Bluetooth serial-style devices only, not a
Pico, ESP32, Arduino, USB serial adapter, `ttyACM` or `ttyUSB`-style board.

The v0.5 firmware HAL remains useful as a board-ready architecture, but v0.7 does not convert it
into physical GPIO/UART/interrupt evidence. The correct next step is a small Pico or ESP32 program
that reuses the same bounded-buffer/state-machine/protocol ideas and records binary size, RAM usage,
timer jitter and UART drop/recovery behavior.

## D. Debugging case study

`labs/debugging_case/main.cpp` contains two disabled-by-default fault fixtures and a fixed path.
`tools/run_debugging_case.sh` builds sanitizer binaries and captures evidence.

The ASan use-after-free fixture did not produce a normal UAF report in this macOS toolchain run;
the runtime aborted inside `sanitizer_malloc_mac.inc`. This is recorded as a limitation rather than
claimed as a success. The UBSan signed-overflow fixture did produce a source-line report and the
fixed path uses an explicit saturating boundary.

## Graduation rule

After v0.7, the repository should stop expanding sideways. Remaining topics such as kernel driver
development, lock-free algorithms, NUMA, production filesystem internals and physical real-time
certification are explicitly outside the current evidence boundary.
